## Medium

### M1: Job creation gets stuck on 409 forever if any job number already exists ahead of the counter

- File: `backend/app/services/job_service.py:69-87`, `backend/migrations/versions/7c4e2a91d5b3_add_sequence_counters.py:25-37`
- What is wrong: The counter starts at 1 for every `(name, year)` with no row, and the migration does not seed it from existing `jobs.job_number` values. If a job with number `CSC-<year>-<n>` exists that the counter did not issue (imported or seeded data, a manual fix, a partial restore, or a counter row deleted or reset), the allocator returns that `n`. The insert then fails on `ix_jobs_job_number`, and the `except IntegrityError` rolls back the job and the counter increment together. Every retry gets the same `n` and fails the same way. Job creation is blocked for the rest of the calendar year, and the response says "Please retry", which can never succeed.
- How to trigger: commit a job `CSC-<current year>-000001` with an empty `sequence_counters`, then call `create_job` three times in separate sessions. Probe result: `CONFLICT 0`, `CONFLICT 1`, `CONFLICT 2` ("The job could not be created. Please retry."), and `sequence_counters` stays empty.
- Impact: Job creation, the centre's main workflow, goes down with no self-recovery. Someone has to fix the counter by hand in the database.
- Suggested fix: (a) Seed or backfill the counter in the migration (or a new follow-up migration, since this one may already be applied) from `max(substring(job_number ...))` per year for rows matching `^CSC-\d{4}-\d{6}$`. (b) Add a DB check, or at least a code comment, that `sequence_counters` must never be decremented. (c) Optionally, on a unique violation of `job_number` specifically, re-sync the counter to `greatest(last_value, max existing)` and retry once, rather than returning a misleading "retry" 409. Add a test for the collision path (see L3).

### M2: Out-of-range integers in IDs and `page` return 500 instead of 4xx

- File: `backend/app/api/v1/routes/jobs.py:40,46,47,64,69`, `backend/app/schemas/job.py:28-29`
- What is wrong: `job_id`, `customer_id`, `service_id` and `page` only have lower bounds (`gt=0` / `ge=1`). The columns are `INTEGER` (int4), and the offset is `(page-1)*page_size` (int8). Values above the column range reach PostgreSQL and raise `DataError` (`NumericValueOutOfRange`), which surfaces as an unhandled 500.
- How to trigger (probe results):
  - `GET /api/v1/jobs/2147483648` returns 500 (`integer out of range`)
  - `PATCH /api/v1/jobs/2147483648` returns 500
  - `GET /api/v1/jobs?customer_id=2147483648` or `?service_id=2147483648` returns 500
  - `POST /api/v1/jobs` with `"customer_id": 2147483648` returns 500
  - `GET /api/v1/jobs?page=100000000000000000&page_size=100` returns 500 (`bigint out of range`)
- Impact: Wrong status codes (a client error reported as a server error), noisy 500s and error logs that anyone can trigger with one request. The DB transaction is aborted. No SQL leaks into the response body (the body is the generic "Internal Server Error").
- Suggested fix: Add `le=2_147_483_647` to `job_id` (`Path`), the `customer_id`/`service_id` query and body fields, and a sensible upper bound on `page` (for example `le=1_000_000`, or derive it so the offset stays within int8). A shared `DbId = Annotated[int, Field(gt=0, le=2**31-1)]` type keeps this consistent. Add tests for each case, expecting 422 (or 404 for path IDs if preferred).

## Low

### L1: `description` has no length limit

- File: `backend/app/schemas/job.py:31,41`
- What is wrong: `description: str | None` has no `max_length` (`TEXT` column).
- How to trigger: `POST /api/v1/jobs` with a 5,000,000-character description returns 201 and stores it (probe confirmed). The same applies to `PATCH`.
- Impact: Unbounded storage and payload growth. Every list page (up to 100 items) returns full descriptions, so one oversized job inflates every listing response that contains it.
- Suggested fix: Add a reasonable `max_length` (for example 5,000 to 10,000) to create and update. Consider trimming or omitting `description` in list items.

### L2: OpenAPI declares the wrong 422 body for the inactive-service rule

- File: `backend/app/services/job_service.py:66`, `backend/app/api/v1/routes/jobs.py:24-31`
- What is wrong: `BusinessRuleError` returns 422 with `{"detail": "<string>"}`, but the generated spec only documents 422 as `HTTPValidationError` (`detail: [ValidationError]`). Generated frontend types will expect an array for this case. This conflicts with the decision that "API responses use consistent error structures".
- How to trigger: `app.openapi()["paths"]["/api/v1/jobs"]["post"]["responses"]["422"]` references `HTTPValidationError`, while `POST` with an inactive service returns `{"detail": "Service is inactive and cannot be used for new jobs."}`.
- Impact: Frontend error handling built from the contract will mis-parse this response.
- Suggested fix: Either document the 422 as `ErrorResponse | HTTPValidationError` in `responses=`, or use a different status or shape for business-rule errors. Raise this as part of the owner's contract re-export.

### L3: Test gaps on the error paths and the year boundary

- Files: `backend/tests/test_jobs_api.py`, `backend/tests/test_job_number_allocator.py`, `backend/tests/conftest.py:77`
- What is missing:
  1. No test reaches the `IntegrityError` to 409 branch (`job_service.py:85-87`). With the `create_savepoint` fixture, `db.rollback()` in that branch also discards the test's own fixture rows (probe: the first call returns 409, then later calls return 404 "Customer not found."), so this path must be tested with committed data, as the concurrency test does.
  2. Nothing tests that the year comes from `Asia/Kolkata` and not UTC (for example, a fixed instant `2026-12-31T19:00Z` must give 2027). `current_year` cannot take an injected clock. A probe of the same SQL expression returns 2027, so the logic is correct, but it is unguarded against regressions.
  3. No test for `get_db` rolling back and closing on an exception.
  4. No tests for the M2 bounds.
- Impact: Regressions in the numbering edge cases would go unnoticed.
- Suggested fix: Add committed-data tests for the conflict path and the M1 scenario. Make `current_year` accept an optional timestamp expression (or test the SQL expression directly with literal instants on both sides of midnight IST). Add the bound tests.

Note on the concurrency test: it genuinely exercises concurrency. It uses 12 threads with separate sessions and connections, released together by a `Barrier`, against committed data with an empty counter table. That covers both the concurrent first-row `INSERT ... ON CONFLICT` and the contended `DO UPDATE`, and the test asserts unique, contiguous numbers. A naive `SELECT max()+1` would fail it. Test isolation is sound: tests run only when `TEST_DATABASE_URL` names a database ending in `_test`, never fall back to `DATABASE_URL`, restore `DATABASE_URL` after the Alembic upgrade (`load_dotenv` does not override the set value), and use `TRUNCATE ... CASCADE` only on the guarded test engine.

## Verified as correct (no finding)

- Job-number allocation: one atomic upsert with `RETURNING`, holding the row lock until commit, in the same transaction as the job insert. A rollback also rolls back the increment, so failed creates leave no gaps. Format `CSC-YYYY-NNNNNN`. The year comes from DB `now()` in Asia/Kolkata.
- Protected fields: `extra="forbid"` on `JobCreate` and `JobUpdate` rejects `job_number`, `status`, `created_by`, `created_at`, `id`, `customer_id` and `service_id` (on PATCH) with 422, and tests assert nothing is persisted. `created_by` is never read from the request. The route passes `None`, and there is a clear `AUTH INTEGRATION POINT` comment in `routes/jobs.py`.
- PATCH: only `title`, `description` and `due_date` change, through `exclude_unset`. An explicit `null` title is rejected, and `description`/`due_date` can be cleared.
- Listing: `page_size` is at most 100, the search escapes LIKE wildcards with an explicit `ESCAPE`, ordering is `created_at DESC, id DESC` (a stable tiebreak), and customer/service are loaded with joins (no N+1). `total_pages` is correct for zero and partial pages.
- Errors: `ServiceError` returns `{"detail": str}` with no DB internals. `get_db` rolls back and closes the session on error.
- Migration `7c4e2a91d5b3`: matches the model (`alembic check` is clean), chains from `31b33db4529a`, and downgrades cleanly. No existing migration was edited.
- No changes outside `backend/`. No new dependencies. Integer IDs are used throughout.
