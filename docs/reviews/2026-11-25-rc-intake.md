# Review: Phase 4.1 registration certificate creates the vehicle

- **Branch reviewed:** `feat/backend-rc-intake` (0e54166; fixes in 45d13fc and a test fix after integration)
- **Reviewer:** independent review agent (Opus 5.5), read-only, probing a copy of the code
- **Integration check:** Sonnet 5.5, over real HTTP with the real OCR worker
- **Date:** 2026-11-25

## Scope

- An admin marks a document type as the registration certificate.
- After OCR, the vehicle intake creates or fills the customer's vehicle automatically.
  - Confident readings are applied.
  - Doubtful fields wait for a person.
  - Values that differ from what is already on the vehicle wait for an "accept".
  - A registration owned by another customer is a conflict.
- New routes: `GET /documents/{id}/vehicle-intake` and `POST .../resolve`.
- New work-queue count: `vehicle_readings_to_check`.

## Findings

| ID | Severity | Finding | Outcome |
|---|---|---|---|
| H1 | High | On a conflict, the reading showed another customer's vehicle id and customer id to an employee who could not see that vehicle. Document access (wider than vehicle access) also let an employee read and overwrite the owner name. | **Fixed.** The vehicle and its current values are shown only to viewers who can see that vehicle. Resolving requires vehicle visibility. A typed registration clash returns 409 and saves nothing. |
| M1 | Medium | `resolve` could change or clear fields that did not wait for a person, without `accept_changes`. | **Fixed.** Only waiting fields are accepted. A null leaves a field as it is. Replacing an existing value needs `accept_changes`. |
| M2 | Medium | An accepted change stored OCR's raw text (e.g. `ma3-fjeb1s 00123456`). | **Fixed.** Cleaned values are sealed with the reading and are what gets applied. |
| M3 | Medium | Confident fields were dropped when the registration was doubtful. | **Fixed.** They are applied on resolve. |
| M4 | Medium | Readings of old versions and archived documents stayed in the queue, and archived ones could still be resolved. | **Fixed.** |
| M5 | Medium | An error in the vehicle step discarded the whole OCR result and made the task retry (extra OCR calls). | **Fixed.** The step runs in a savepoint: a registration clash is retried once, and other errors leave the reading for a person. The OCR result is always kept. |
| M6 | Medium | Contract: `WorkQueueSummary` gains a required field. | **For the owner** to approve in the contract PR. |
| L1 | Low | Short identifiers were nearly visible when masked. | **Fixed.** Under 6 characters is fully masked. |
| L2 | Low | A mistyped registration conflict linked the wrong vehicle permanently. | **Fixed.** Nothing is saved on a clash. |
| L3 | Low | Category mapping: cabs were not counted as commercial, and an accept could set "other" over a real category. | **Fixed.** |
| L4 | Low | Worker actions were audited as the uploader, and inactive users could be made responsible. | **Fixed.** No user is recorded on worker actions, and only active employees are assigned. |
| L5 | Low | A later `/ocr/review` correction does not reach the vehicle. | **Recorded.** The vehicle is edited directly or through the intake. |
| L6 | Low | Queue scoping is uploader- or responsible-based. | **Recorded.** |
| L7 | Low | Test gaps. | **Added** for every fix above. |

## Integration check (real HTTP, real worker)

All 6 steps passed:

1. An RC type without a `registration_number` field returns 422.
2. A clean RC creates the vehicle automatically:
   - masked identifiers, the right category, assigned to the uploader, status `applied`, queue count 0
   - the audit records no user and contains no identifier values
3. A doubtful engine number: only that field waited. Reveal was audited, and resolving cleared the queue. A field that was not waiting returned 422.
4. A conflict with another customer's registration showed no vehicle and no ids, returned 409, and left the other vehicle untouched.
5. The contract changes are additions only.

The agent also found a brittle test: it searched for an id as plain text, so a one-digit id could match a timestamp. It now checks the id fields themselves.

**Owner notes from integration:**
- A reading counts as `resolved` even when a waiting field was left empty on purpose (null).
- The 409 message names "another customer's vehicle" for a registration the employee typed.
