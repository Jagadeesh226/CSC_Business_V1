## Low

### L-1: Audit details store the amount as the client typed it, not in the stored 2-decimal form

- **File:** `backend/app/services/fee_service.py:117` (`_add`, `"amount": str(fee.amount)` before commit), `backend/app/services/fee_service.py:171` (`update_fee`, `"new": str(v)`)
- **What is wrong:** `str()` is applied to the Decimal that Pydantic parsed from the request, before the database rounds it to `NUMERIC(12,2)`. The audit therefore records `"100.5"`, `"1E+2"` or `"5.000"`, while the API returns and stores `"100.50"`, `"100.00"` and `"5.00"`. In `fee_updated`, `old` is in database form and `new` is in request form, for example `{"old": "5.00", "new": "2E+1"}`. `fee_removed` (line 199) is not affected, because it reads a value loaded from the database.
- **How to trigger:** `POST /api/v1/jobs/{id}/fees` with `"amount": "1e2"`, or with the JSON number `100.5`. `PATCH` with `"amount": "2e1"`. See probe 1.
- **Impact:** The value is numerically correct, but the audit trail for money uses mixed and scientific formats. Anyone reading or exporting audits (or comparing them to receipts) has to normalise first. No data loss.
- **Suggested fix:** Quantize once at the schema boundary, for example with an `AfterValidator(lambda d: d.quantize(Decimal("0.01")))` on `Amount`. Alternatively, write `f"{amount:.2f}"` in the audit. Add an audit assertion using a non-canonical input such as `"1e2"`.

### L-2: A fixed-fee service with a 0.00 default creates a zero-amount fee that the API itself would reject

- **File:** `backend/app/services/fee_service.py:137` (`add_default_service_fee`), `backend/app/models/service.py` (`ck_services_default_fee_nonnegative` allows 0)
- **What is wrong:** The API requires fee amounts `> 0` (builder default), but the automatic fee is added whenever `default_service_fee is not None`, including `0.00`. The job then carries a `service` fee of `0.00` that an admin cannot edit back to `0` and that an employee could not have created.
- **How to trigger:** Create a job for a fixed-fee service whose `default_service_fee` is `0.00` (for example a free service). See probe 2.
- **Impact:** A cosmetic, empty fee line on free-service jobs. The invariant "every fee is > 0" does not hold, which later Phase 3 or receipt code might assume. Totals are unaffected.
- **Suggested fix:** Skip the automatic fee when `default_service_fee <= 0` (`if service.fee_type == "fixed" and service.default_service_fee`). Alternatively, if the owner wants a ₹0 line, document that zero-amount fees are allowed. Add a test either way.

### L-3: Downgrading the migration turns removed fees back into active fees

- **File:** `backend/migrations/versions/e1a2b3c4d5f6_add_job_fee_removal_columns.py:33-37`
- **What is wrong:** `downgrade()` drops `deleted_at` and `deleted_by`, but keeps the rows that were removed. On the previous schema, every remaining row counts as an active fee, so removed fees come back into job totals. The removal is then recorded only in the `fee_removed` audit details.
- **How to trigger:** Remove a fee, then run `alembic downgrade d8e3f4a6b7c9`. The removed fee is now an ordinary fee.
- **Impact:** Only on a rollback. Fee totals silently change for every job that had a removal. This matters once payments or receipts reference those totals.
- **Suggested fix:** In `downgrade()`, refuse when removed rows exist (`SELECT 1 FROM job_fees WHERE deleted_at IS NOT NULL LIMIT 1`, then raise). Alternatively, document in the docstring that downgrade is only safe before any fee has been removed. Do not hard-delete in downgrade, because that breaks the "never erased" rule.

### L-4: Test gaps for audit reasons, removal audit and the admin write locks

- **File:** `backend/tests/test_job_fees.py:84` (`test_fixed_fee_service_adds_default_fee`), `:236` (`test_admin_removes_fee_but_keeps_it`), `:373` (the only race test)
- **What is wrong:**
  - No test checks the `fee_added` audit for the automatic fee. Its `reason: "service_default"` and its `user_id` (the creator) are not covered.
  - No test checks the `fee_removed` audit at all. The action name, `fee_id`, `amount` and `user_id` are not covered.
  - The race test covers only an employee add against a payment. Nothing fails if `update_fee` or `remove_fee` stop locking the job. The current code is correct; this is a regression guard only.
  - There is no test that an employee cannot add a fee after being unassigned (formerly assigned gives 404).
- **How to trigger:** Delete the `audit_service.record` call in `remove_fee`, or the `reason` argument in `add_default_service_fee`, and run the suite. It stays green. (Checked by reading the tests. Mutation not run for these.)
- **Impact:** Test gap only. §14 requires auditing of job changes, so these audit rows should be covered.
- **Suggested fix:** Assert the `fee_added` audit (with `reason`) in the default-fee test. Assert the `fee_removed` audit in the remove test. Add a formerly-assigned-employee 404 case. A two-session test for remove-vs-remove (the second request gets 404) is optional.

### L-5: Every write re-reads all of the job's fees to return one

- **File:** `backend/app/services/fee_service.py:56-60` (`_read_one`)
- **What is wrong:** After each add or edit, `_read_one` runs the full `list_fees` query (with removed fees) and scans it in Python for the one fee id.
- **How to trigger:** Any `POST` or `PATCH`. The cost grows with the number of fees on the job.
- **Impact:** Negligible at CSC scale, since a job has a handful of fees. It is noted because the repository already has a per-job, per-id filter pattern.
- **Suggested fix:** Add a `get_fee_row(db, job_id, fee_id)` that uses the same joins plus `JobFee.id == fee_id`.

## Accepted gaps (owner decisions, not findings)

- **Contract:** `docs/contracts/openapi.json` is not updated for the four fee routes, so `check.sh` reports contract drift. Owner PR pending. Notes for that PR:
  - Response `amount` and totals are typed `{"type": "string"}` (Pydantic v2 serialises Decimal as a string, for example `"100.00"`). Good for money, but the frontend must treat them as decimal strings.
  - Request `amount` is `anyOf [number > 0, string]`. The string branch carries no `pattern`, `maxDigits` or `decimalPlaces` in the spec, although the server enforces them (422). Clients learn the limits only from errors.
- **Phase 3 lock:** the payment-received rule is race-safe only if Phase 3 payment recording takes `get_job_for_update` on the job before inserting a `received` payment. Nothing records payments today. The branch's race test (verified by mutation, probe 3) documents the required behaviour. The Phase 3 review must check it.
- **Payment status:** only `status = 'received'` blocks employees. A later refunded or voided payment would allow employee adds again. This follows the owner rule literally.
- **Admin rights:** admins add, edit and remove fees on closed jobs and after payment, for corrections. Removal is soft. Employees cannot add to closed jobs. Amounts must be `> 0` with 2 decimals.
- **Employee scope:** employees may add only to jobs they are *assigned* to (permissions.md says only "until a payment is received"). This is consistent with the rest of the job permissions.
- **Totals:** one job's total can exceed `NUMERIC(12,2)` (probe 8 summed three maximum fees to `29999999999.97`). The API returns it correctly. Phase 3 payments are also `NUMERIC(12,2)`, which is only a concern for unrealistic amounts.

## Checked and correct

- **Money:** `Decimal` end to end. Pydantic `Decimal` with `gt=0`, `max_digits=12`, `decimal_places=2` matches `NUMERIC(12,2)`, and Pydantic counts whole digits correctly for exponent forms (`1E+10` rejected). NaN, Infinity, booleans and imprecise floats are rejected. Responses are built after commit from rows reloaded from the database (`expire_on_commit` default), so amounts are always 2-decimal strings. Totals are summed in SQL per type, with `Decimal("0.00")` defaults for missing types, then added in Python with `Decimal`. There is no float anywhere. The DB check `amount >= 0` is a second guard.
- **Authorization and IDOR:**
  - `GET` and `POST` call `ensure_job_access`. Unassigned or formerly assigned employees get 404, the same as for a missing job.
  - `PATCH` and `DELETE` use `AdminUser`, so an employee gets 403 whether or not the job or fee exists (no existence leak).
  - `get_active_fee` filters by `job_id` and `fee_id`, so a fee from another job gives 404 (tested).
  - `include_removed` shows removed fees only to users who can already see the job.
  - Writes need sign-in (401) and CSRF (403). Path ids are bounded to int4 (422 above).
- **Payment-received rule:** checked after the job lock, for employees only. A `pending` payment does not block (tested). The rule is race-safe given the Phase 3 lock (see Accepted gaps).
- **Closed jobs:** the employee status check runs on the locked row (`populate_existing`), so a concurrent completion is seen. Admins bypass it by design.
- **Soft delete:**
  - Removal sets `deleted_at` and `deleted_by`, and the row is kept (tested).
  - A second `DELETE` and any `PATCH` on a removed fee give 404 (tested).
  - Totals always exclude removed fees, including with `include_removed=true` (tested).
  - Two concurrent removals serialise on the job lock, and the second gets 404.
- **Lock order:** every fee write takes `FOR UPDATE` on the job only. The inserts' foreign keys to `users` (`created_by`, `deleted_by`, `audit_logs.user_id`) take `FOR KEY SHARE`, which does not conflict with deactivation's `UPDATE users`. Deactivation locks jobs, then the user, the same order. Probes 4 and 5 show both interleavings serialise correctly with no deadlock. Assignment, unassignment, status changes and cancel also lock the job first, so they serialise with fee writes.
- **Transactions:** one commit per operation. Errors before commit roll back through `get_db`. The automatic default fee and its audit are inside `create_job`'s existing transaction and retry loop, so a job-number collision rollback recreates them with the job.
- **Audit:** `fee_added`, `fee_updated` (only when something changed, with old/new) and `fee_removed`, with `entity_type="job"`, `entity_id=job_id`, `fee_id` in the details, and the acting user. The amount format issue is L-1, and the test gaps are L-4.
- **Circular import:** `job_service` imports `fee_service`, and `fee_service` imports `job_service`. Both import with plain `from app.services import ...` and use attributes only inside functions, so either import order works (probe 7). Keep it that way: a module-level `from app.services.job_service import X` in `fee_service` would break it.
- **Validation and status codes:**
  - `extra="forbid"` on create and update.
  - Descriptions are stripped, 1–500 characters.
  - An explicit `null` in a `PATCH` gives 422. An empty `PATCH` gives 200 and no audit.
  - Unknown `fee_type` gives 422. Rule violations give 422 with a clear message. Unknown job or fee gives 404. Create gives 201 and delete gives 204.
- **Queries:** the list is one query with two aliased outer joins (no N+1), plus one grouped totals query. It is unbounded per job, which is acceptable for fees. `payments.job_id` is indexed for the `EXISTS` check.
- **Migration:** single new revision on head `d8e3f4a6b7c9`. Nullable columns, a named foreign key that matches the model. Reversible structurally (probe 6). The data aspect of downgrade is L-3.
- **Renames:** `_is_admin` and `_ensure_job_access` became public `is_admin` and `ensure_job_access`. All call sites were updated. There is no behaviour change.
- **Test changes:** `test_jobs_api.py` filters audits to `job_%` actions. That is needed because fixed-fee test jobs now also write `fee_added`. The assertions are unchanged, so this does not weaken them.
- **AGENTS.md:** changes only under `backend/`. No contract edits, no new dependencies, integer ids throughout. Fake data in tests. No scope creep (no payment or receipt recording).
